# データ設計（Firestore）

## 11/8 Aの追加4機能

- 先生の返信と同じトランザクションで `courses/{courseId}/enrollments/{uid}/notifications/{notificationId}` を作る。IDは質問IDと発言sequenceのSHA-256で固定長にする。項目は `questionId, messageId, title, createdAt, readAt`。通知は本人だけが取得・既読化できる。既読は再送で書き換えない。
- 新しい質問の省略可能な `relatedQuestion` に、同じ講義の本人の元質問ID・タイトル・最大10発言のスナップショットを保存する。画面では本人用の詳細APIで元の会話を読み、同じチャット内で新しい発言との境目を表示する。元会話と新しい質問は別のIDで保存する。公開Q&Aには元会話を含めない。
- AI回答には元会話のスナップショットを前置し、現在の会話を優先して合計20発言以内にする。保存済みの会話順序を変更せず、AIへ渡す入力の順序だけを振り直す。
- 新しい別案の再生成は既存の版・試行管理を使用する。参照Q&Aの詳細は公開用の5項目だけを返す。

## 現在の設計

### 基本方針

- Next.js / Firebase App Hosting / Firestore Admin SDK / Firebase Authentication（Google、メール／パスワード）/ Vertex AI（Gemini）。
- ブラウザの Firebase SDK はログイン（firebase/auth）だけ。Firestore はブラウザからの直接アクセスを全面拒否し、サーバー経由で読み書きする。Admin SDK はセキュリティルールを通らないので、コードの中で権限を確認する（`src/server/auth/access.ts`）。
- 原文・本人情報、確認中の候補と版、公開Q&A を分ける。Firestore のレコードをそのまま画面へ返さない（`src/server/firestore/dto.ts` で返してよい項目だけにする）。
- AI の回答を直接 knowledge に登録しない。公開は教員の明示操作だけ。

### 認証と URL

- 生徒・教員とも Google でログインできる。審査用に、Firebase Authentication で登録済みのアカウントはメール／パスワードでもログインできる。アプリにはアカウント登録画面を設けない。
- どちらの方式でもサーバーが ID トークンを検証し、httpOnly のセッション Cookie（`__session`、5日）に交換する。ページと API で Cookie を検証する。メールを使った講義作成・教員権限の判定には検証済みメールを使う。
- Google のポップアップを閉じた後は同じ画面で再試行できる。ポップアップの終了が通知されない場合は、ログイン画面のキャンセルボタンから操作を再開できる。
- 本人の識別は検証済みの uid。担当教員は `courses.teacherEmails` と検証済みメールで判定する。新規講義を作成した本人は、その講義の担当教員になる。ブラウザの uid・役割・メールは使わない。
- 生徒は固定の参加URL（`/join/{courseId}`）を開くか、講義一覧で共有ID（講義IDと同じ値）を入力する。初回はログインと有効な参加コードの照合を経て、uid と講義の参加関係を保存する。別端末でも同じアカウントなら参加済み。名簿照合・学籍番号入力はしない。
- 担当教員は講義の設定から固定の参加URL・共有IDを確認し、参加コードを発行できる。コードは発行から30分で失効する。再発行・無効化の対象はコードで、参加済みの生徒は引き続き利用できる。期限のない旧コードは失効扱いとする。
- 生徒は `/c/{courseId}`、教員は `/t/{courseId}`。参加コードは参加時の POST 本文と担当教員への発行応答だけで扱い、URL・ログ・公開 DTO に載せない。DB にはハッシュを保存する。コード照合に同じアカウントで5回失敗すると、最後の失敗から10分間停止する。失敗の間隔が10分以上空いたら回数をリセットする。
- `/` はログイン済み利用者の講義一覧。参加済み講義と担当講義をサーバーで照合し、同じ講義で兼任なら両方の入口を出す。「講義を作成」から `/courses/new` へ進み、担当講義から生徒を招待できる。
- `/courses/new` は検証済みメールを持つログイン済み利用者が使う。講義名（前後の空白を除いて1〜80文字）を入力すると、新規講義に本人の検証済みメールと初期カテゴリ「その他」（`other`）を保存し、教員画面を開く。同じ作成要求を再送しても講義は1つだけ作る。
- 未ログインで `/`・講義作成ページ・生徒ページ・教員ページを開くと `/login` へ進む。ログイン済みで `/login` を開くと、許可されたページか `/` へ移る。ログインの `next` は講義作成ページと、生徒・教員ページの認識済みの表示クエリを受け付ける。
- 参加URLを開いた場合は参加画面内でログインし、同じ画面でコードを入力する。旧URLの `code` クエリは取り除く。参加成功後は参加ページの履歴を生徒ページで置き換える。
- 講義APIが401を返したら講義画面と定期取得を終了し、再ログイン後に同じ講義画面へ戻る導線を出す。ログイン・ログアウト・参加の成功後はブラウザでページを読み直す。
- 講義ページの中の画面は URL のクエリで表す。ブラウザの戻る・進む、再読み込み、ログイン後の復帰で同じ画面に戻れるようにする。質問 ID は秘密の値ではなく、見られるかどうかは毎回サーバーで確認する。
  - 生徒：`/c/{courseId}`（新しい質問）、`?view=history`、`?view=shared`、`?question={質問ID}`、`?relatedTo={質問ID}`（解決した質問の続きを書く画面）
  - 教員：`/t/{courseId}`（質問対応）、`?view=review`、`?view=published`、`?view=settings`。開いている質問は `?question={質問ID}`（質問対応・Q&A確認）、見送った候補は `?view=review&dismissed={質問ID}`
  - URL に載せないもの：入力途中の文章、検索・絞り込み、通知の一覧、確認用の小さなダイアログ
- 担当教員には相談作成時点のアカウントの表示名（なければ検証済みメール）を見せる。後の名前変更は過去の相談に反映しない。他の生徒には匿名。
- ローカルでは Auth Emulator（9099）と Firestore Emulator（8080）を使う。

### 保存先

| パス | 保存する情報 |
| --- | --- |
| `courses/{courseId}` | name、teacherEmails、categories（id/name/order、担当教員が追加・編集）、materials |
| `courses/{courseId}/enrollments/{uid}` | 講義参加（uid、inviteId、joinedAt） |
| `courses/{courseId}/invites/{sha256(courseId:code)}` | active、createdByUid、createdAt、revokedAt、expiresAt（既定 null）。生のコードは保存しない |
| `courses/{courseId}/questions/{questionId}` | studentId=uid、studentDisplayName（作成時に固定）、title、categoryIds、status、escalatedBy、resolvedAt、messageCount、aiAttempt（試行IDと期限）、lastErrorCode、draft（候補状態の複製） |
| `…/questions/{questionId}/messages/{6桁の sequence}` | role、text、sequence、referencedKnowledgeIds、lowConfidence（自信のない AI 回答） |
| `courses/{courseId}/knowledgeDrafts/{questionId}` | 相談に一意の候補。publication（none/published/dismissed）、selectedVersionId、versionCount、activeGeneration、lastGeneration、publishedVersionId、publishedKnowledgeId |
| `…/knowledgeDrafts/{questionId}/versions/{versionId}` | 版（generated / teacher_edit）。question、answer、categoryId、生成に使った会話の最後の sequence |
| `…/knowledgeDrafts/{questionId}/generations/{generationId}` | 生成の試行（running / succeeded / failed）。失敗の errorCode は summary_failed・summary_configuration_failed（AI の設定エラー、11/8）・expired（期限切れ、復帰時に閉じた古い試行を含む） |
| `courses/{courseId}/knowledge/{knowledgeId}` | 公開Q&A。question、answer、categoryId、publishedAt、内部用の sourceQuestionId・sourceVersionId。取り下げでドキュメントごと削除する（11/8。削除の履歴は残さない） |

### 相談の状態遷移

- pending → ai_answered / escalated（AI が自信なし）/ error。AI の試行は 90 秒で期限切れとし、期限後は error として扱う（期限後に届いた回答は保存しない）。再試行は保存済みの発言を使う。
- ai_answered・teacher_answered・error から生徒が追記すると pending（AI 回答待ち）。
- **escalated の間に生徒が追記すると、補足として保存して escalated のまま（AI は呼ばない）**（11/7 決定）。
- escalated → 教員の返信 → teacher_answered。teacher_answered から再び先生に相談すると escalated。
- resolvedAt は生徒の解決操作だけで設定する。教員の返信・候補作成・再生成・公開では設定しない。解決後は追記できず、新しい相談にする。

### 共有候補

- 生徒の解決操作、または担当教員の明示操作で要約の生成を予約する。解決時に要約の材料となる回答が一つもない場合は `sharingExcluded` を記録し、非共有のまま解決する。自信がなく引き継いだAIの発言は回答に数えない。候補を作らず、解決後の要約の再試行や別案作成も受け付けない。すでに公開されているQ&Aは教員が取り下げるまで維持する。
- 生成の要求は相談が pending（期限内）でなければ受け付ける。生成中は解決・二重の生成を拒否する（1候補につき1つ）。
- 生成結果は常に新しい版として追加し、選択中の版・教員編集版・公開本文を上書きしない。生成は 120 秒で期限切れとし、期限後に届いた結果は保存しない。
- 解決時に候補・教員編集版があっても残し、解決時点までの会話から新しい別案を1つ作る。
- 会話の追加で候補を自動更新しない。自信のない AI 回答は要約の素材から除く。
- 要約に渡す会話は最大20発言。超える場合は初回質問と直近の発言を使い、直近に回答がなければ最も新しい回答も含める。回答・要約の入力では、生徒の発言と教員の返信は各2,000文字まで、保存済みのAI回答は各4,000文字まで扱う。
- 教員の編集は教員編集版として追加し、公開は選んだ版と内容で行う。同じ内容の再送は同じ結果、別の内容は競合。
- 生徒には候補の本文を返さず、状態と操作可否だけを返す。
- AI の設定エラー（`getAiWorkflow()` が失敗）も生成の失敗として記録し、相談・解決日時・既存の版・教員編集版・公開本文は変えない。失敗の記録自体ができなければ成功扱いにしない（11/8）。
- **見送りからの復帰**（11/8）：担当教員が `publication` を dismissed から none に戻す。版・選択中の版・カテゴリ・生成の履歴は残し、AI は呼ばない。生成中・確認できる版がない・公開中は拒否。期限切れのまま残った試行があれば、同じトランザクションで expired として閉じる。相談の `draft`（複製）も同時に更新する。
- **公開の取り下げ**（11/8）：担当教員が knowledge を削除し、同じトランザクションで元候補（`sourceQuestionId`）を none に戻して `publishedKnowledgeId`・`publishedVersionId` を消し、公開していた版を選択する。版の履歴・相談の状態・resolvedAt は変えない。元候補の現在の公開と一致しない knowledge は削除しない（409）。元候補がない初期データ（seed）は削除だけ。別案の生成中でも取り下げられ、生成結果は別案として追加される。再公開は新しい knowledgeId になり、古い ID の取り下げは 404。
- 取り下げた Q&A は公開一覧・1件取得・AI に渡す公開Q&A から消える。過去の会話の `referencedKnowledgeIds` は書き換えず、参照先の取得は 404 になる。

### 検索・カテゴリ・公開レスポンス

- 初回質問を Gemini で最大2カテゴリに分類し、サーバーで講義の現行カテゴリ ID と照合する（有効なものがなければ other）。追加質問は保存済みのカテゴリを使う。
- 回答には同じ講義・カテゴリ一致の公開Q&A を新しい順に最大30件渡す（初期値）。公開Q&A は教員確認済みのものだけ。
- `PublishedKnowledgeDTO` は id/question/answer/categoryId/publishedAt だけ。
- 既存データの移行はしない。デモデータは `npm run seed:demo` で作る。

### アクセス

役割は「参加済み生徒」と「担当教員」の2つ（11/7 決定）。兼任でき、生徒用の API・画面では生徒としてだけ振る舞う（`studentView`、11/8）。

| 主体 | できること |
| --- | --- |
| 参加済み生徒 | 自分の相談の投稿・閲覧・追記・相談・解決・候補の再生成要求、同じ講義の公開Q&A の閲覧 |
| 担当教員 | 担当講義の原文と本人表示の閲覧、返信、候補の作成・再生成・編集・公開・見送り・見送りからの復帰、公開の取り下げ、カテゴリ追加・編集、招待の発行 |
| それ以外 | 何もできない（非公開データは 404） |

## 保留事項

- 講義管理者・全体管理者（校長役）・相談単位の原文閲覧許可・既存講義への教員追加画面は保留。将来の要件は[確認済み要件の権限表](confirmed-requirements.md#権限)。実装時は管理権限と原文閲覧権限を分け、全講義を管理できることを全原文への無条件アクセスと解釈しない。管理者の自己教員付与は拒否から始める。
- 復帰・取り下げの画面と Route Handler は B が実装する（C のストアは 11/8 に実装済み）。公開中の候補への編集・選択・公開は 409 のままで、直すときは取り下げてから編集・再公開する。
- カテゴリの削除は未合意。過去の相談への関連付けは11/8の追加仕様に従う。
